План для исполнителя-ИИ. Норматив: `CONSTRAINTS_AND_POLICY.md` (пункты 1–3 меняют §7 и §8; сначала код по этому плану, политику подтянуть в пункте 4, не наоборот). Язык: **Go**.

Работа **только по пунктам**. К следующему не переходить без явного апрува. Если план и политика расходятся — остановиться и спросить, не импровизировать. PII-порог, Excel ≤5 листов, формат ячейки CSV, корни `combo`/`db` не переоткрывать.

Пункт 0 **закрыт** ответами заказчика. Новых правил сверх них не выдумывать.

## Цель

1. Висящая строка прогресса верхней папки с секундами, обновление раз в секунду.
2. Лог по каждой верхней папке и `converted.txt` **только если получен хотя бы один CSV**. Пустую папку и папку с нулём CSV не помечать завершённой.
3. `.sql`, у которых первая строка — табличная шапка (не SQL), предупредить и переложить в наш CSV рядом. Исходник не менять. PII тот же, что у INSERT.

## Пункт 0. Принятые правила (код не писать в этом пункте)

Это зафиксированные ответы. Ниже — рабочая спецификация для пунктов 1–4.

### 0.1. Прогресс

Оставить висящую строку верхней папки, добавить время обработки в секундах. Обновлять **раз в секунду**, даже если файл тот же (чтобы было видно, что процесс жив, а не завис). Счётчик — **всей верхней папки**, не каждого файла. Формат:

`папка в обработке: <имя> (<N> с)`

`<имя>` как сейчас (`TopFolder`, для файлов в корне — `корень`). `N` — целые секунды с момента, когда эта верхняя папка стала текущей. Верхние папки по-прежнему строго по одной.

Не писать в эту строку путь файла, `3/10`, число INSERT, VALUES, ячейки.

### 0.2. `converted.txt`

Дописывать имя верхней папки **только если в этом запуске для неё создан хотя бы один CSV** (неважно, из SQL INSERT, табличного `.sql` или Excel).

Не дописывать:

- нет ни `.sql`, ни `.xlsx`/`.xls`;
- рабочие файлы были, но **ноль** CSV (все INSERT/табличные отсеял PII, не было VALUES, книги >5 листов без CSV, сплошные ошибки открытия).

Excel конвертится **независимо** от наличия SQL: нет SQL — Excel всё равно обрабатываем. Это не повод писать папку в `converted.txt` «потому что sql не было». В список она попадает только из‑за факта CSV.

Файлы прямо в корне по-прежнему не входят в `converted.txt`.

Оборванная папка (процесс убит) — имени нет, следующий запуск обрабатывает снова.

### 0.3. Лог папки (обязательные строки)

На **каждую верхнюю папку** ровно такой итог (плюс висящий прогресс из §0.1):

| Ситуация | Консоль | `converted.txt` |
|---|---|---|
| Нет ни `.sql`, ни Excel | есть строка, что нет файлов | нет |
| Сконвертили хотя бы один файл (есть ≥1 CSV) | папка обработана | да |
| Не смогли сконвертить (0 CSV) | ошибка и **почему** | нет |

Если часть файлов упала, но ≥1 CSV уже есть — папка обработана и в `converted.txt`; ошибки упавших единиц **всё равно** писать, с причиной.

Не логировать каждый успешный INSERT, каждый PII-пропуск и каждый `SELECT`/`SET` по отдельности. Итог папки — по таблице выше. Если папка закончилась с 0 CSV, в ошибке указать реальную причину (нечего конвертировать / всё отсеял фильтр / не разобрать / не записать), без тел VALUES и без содержимого ячеек.

Формулировки (смысл зафиксирован, точный текст можно сделать стабильным для тестов):

- нет рабочих файлов: `папка <имя>: нет файлов`
- успех: `папка обработана: <имя>` (вместо нынешнего `папка полностью завершена`)
- провал: `error: папка <имя>: не создано ни одного CSV: <причина>`

### 0.4. Ошибка INSERT при уже записанном CSV

CSV **оставлять**. Первый успешный INSERT ключа уже на диске — поздний провал того же ключа его не удаляет (как §6).

В лог обязательно причина провала этой единицы: путь `.sql`, имя таблицы, конкретная ошибка (`значений больше, чем колонок`, не разобрать INSERT, не создать/записать CSV). Сейчас часть таких провалов тихая, из‑за этого «ошибка таблицы есть, CSV тоже есть, непонятно что случилось». Ячейки и VALUES в лог не писать.

### 0.5. Табличные `.sql`

Детектор **по первой непустой строке**, не сканировать весь файл в поисках `INSERT`:

- строка — шапка таблицы;
- это не SQL-выражение (не начинается как `INSERT` / `CREATE` / `UPDATE` / `DELETE` / `WITH` / `BEGIN` / `ALTER` / `DROP` / `REPLACE` / `TRUNCATE` и не `INSERT` после префиксов);
- разделитель — один из CSV: запятая, точка с запятой, таб. Выбрать по первой строке тот, который даёт больше полей (≥ 2). Если ни один не даёт ≥2 полей или строка — SQL, идти в обычный `insert.Parse`.

Имя CSV: `{stem}.sql` → `{FileBase(stem)}.csv` в той же директории (`GameSalad.sql` → `GameSalad.csv`). Ключ записи тот же, что у INSERT: `(директория, основа имени)`. Варианты `(n)` не плодить. Исходный `.sql` не менять.

PII **действует**: имя таблицы = stem файла без расширения; колонки = шапка. Правило как у INSERT: stem прошёл `pii.Match` **или** `pii.MatchColumns(шапка)`. Иначе файл не даёт CSV (после warn, см. ниже).

Писать **наш** CSV §6 (кавычки, запятая, LF, без BOM), не копировать исходные байты. Шапка → первая строка CSV, дальше строки данных.

Одна `warn` на такой файл: путь и причина, что это не INSERT, а таблица. Без дампа строк.

Поток: не `ReadFile` целиком. Первая строка для детекта, дальше построчно в CSV. Буфер сканера достаточно большой для длинной шапки; файл в сотни МБ не держать в памяти.
