# Constraints and Policy

Документ задаёт обязательные правила для реализации консольного конвертера SQL/Excel → CSV. Любое отклонение от этого документа требует явного согласования с заказчиком.

## 1. Цель

После запуска спросить `combo` или `db` и рекурсивно пройти выбранный корень (`C:\Source\combo` или `C:\Source\db`), на любой глубине найти:

- файлы `.sql` — извлечь `INSERT ... VALUES` (PII по таблице или минимум двум зачётным колонкам) и табличные дампы со шапкой в первой непустой строке (§4.2); CSV **рядом с исходным SQL**; после полной обработки этого файла исходный `.sql` **удалить** (§15);
- файлы `.xlsx` и `.xls` — сохранить CSV **рядом с исходным Excel** по правилам §13; после полной обработки книги исходный Excel **удалить** (§15);
- файлы `.csv` и `.txt` — в том числе существовавшие до запуска программы: если строк данных больше 4_000_000 — нарезать по §14.

В выбранном корне хранятся четыре независимых списка верхних папок: `_convert_done_.txt`, `_convert_passed_.txt`, `_splitter_done_.txt` и `_splitter_passed_.txt`. Списки закрывают только соответствующий этап; полностью папка пропускается после закрытия обоих этапов. Полный контракт состояний описан в §7.

Конвертер — консольное приложение. Исходной папки на момент разработки может не быть: это нормально. Если при запуске выбранный корень отсутствует — приложение **завершается с ошибкой** (ненулевой код выхода), ничего не создаёт.

## 2. Язык и стек

**Язык: Go.**

Почему не Python:

- файлов много, отдельные файлы могут быть большими;
- нужен потоковый разбор SQL (не `ReadFile` / не загрузка всего SQL в память);
- независимые задачи (INSERT, листы, существующие CSV, разные директории и верхние папки) обрабатываются конкурентно с **одним глобальным пулом** воркеров (§9);
- результат — один бинарник без интерпретатора и venv.

Запрещено:

- подключать полный SQL-движок или ORM;
- тащить тяжёлые парсеры «всего SQL»;
- читать весь `.sql` в `[]byte` / `string`, если размер может быть большим;
- писать свой разбор ZIP/XML Excel или BIFF/OLE `.xls` с нуля.

Разрешено: стандартная библиотека Go + минимальные зависимости только если без них нельзя закрыть требование. Для `.xlsx` и `.xls` допустимы библиотеки чтения Excel (например `excelize` для `.xlsx`), без Excel COM и без запуска Excel.

| Выбор корня | после запуска (кроме `--help`) приглашение `combo/db:`; регистр не важен; пустой / неизвестный / EOF — ошибка, exit 2 |

## 4. Что извлекать из SQL

Из `.sql` извлекаются `INSERT` с данными в форме `VALUES` и табличные дампы (§4.2). Исходный `.sql` **не править** (не перезаписывать, не обрезать). После полной обработки файла его **удалить** по §15.

В scope:

- `INSERT INTO table (...) VALUES (...);`
- `INSERT table (...) VALUES (...);` и `INSERT table VALUES (...);` — ключевое слово `INTO` необязательно;
- `INSERT INTO table (...) VALUES (...), (...), (...);` — один INSERT даёт несколько строк данных в CSV этой таблицы (не отдельный файл на каждую строку `VALUES`)
- `INSERT INTO table VALUES (...), (...);` — без списка колонок; CSV **без** строки заголовка; ширина = первая строка `VALUES`
- опциональные префиксы вроде `INSERT IGNORE`, `INSERT OR REPLACE`, `LOW_PRIORITY`, `DELAYED` — таблица и колонки всё равно извлекаются
- идентификаторы: `` `table` ``, `"table"`, `[table]`, `schema.table`, `db.schema.table` (имя файла = последний сегмент, без схемы)
- строковые литералы `N'...'` и `E'...'`; префикс не попадает в значение ячейки
- строковые литералы `'...'`, `"..."`; экранирование `''` внутри одинарных кавычек
- внутри `'...'` и `"..."` символ `\` экранирует следующий символ: `\'` и `\"` не закрывают литерал, `\\` — один обратный слэш. Escape-последовательности не разворачиваются: `\n` остаётся двумя символами текста
- двойные кавычки трактуются по позиции: в позиции имени таблицы или колонки — идентификатор, в позиции значения внутри `VALUES` — строковый литерал
- значения в скобках: числа, `NULL`, строки, hex-литералы как текст ячейки

Вне scope (пропустить INSERT; `SELECT` / `SET` / отказ PII в консоль не писать — см. §8):

- `INSERT ... SELECT ...`
- `INSERT ... SET col=val` (нет `VALUES`)
- `INSERT INTO t () VALUES (...)` — пустые скобки списка колонок
- DDL, `UPDATE`, `DELETE`, хранимые процедуры, комментарии сами по себе
- оборванный концом файла `INSERT` после одной или нескольких целых строк — целые строки записать, сообщить об обрыве по §8 и оставить исходник; если целых строк нет, CSV из этого INSERT не создавать
- синтаксически битый `INSERT` посреди файла — CSV из него нет; если разбор уже начался после `Begin`, причина пишется по §8, уже записанный CSV того же ключа не удаляется; строки с лишними значениями (§6) не отменяют весь INSERT
- `INSERT` с пустым набором строк данных (после `VALUES` нет ни одной группы значений): CSV из одного заголовка не создаётся

Комментарии `-- ...` и `/* ... */` не должны ломать поиск `INSERT`. MySQL-хинты вида `/*!40101 ... */` трактуются как обычный блочный комментарий, их содержимое игнорируется целиком. Строки внутри кавычек и тела Postgres `$$...$$` / `$tag$...$tag$`, похожие на SQL, не считаются синтаксисом. Слово `INSERT` без следующего имени таблицы, например в `GRANT INSERT`, тихо пропускается.

### 4.1. Фильтр PII для SQL

Успешно разобранный `INSERT ... VALUES` писать в CSV, если выполняется хотя бы одно условие:

- имя таблицы без схемы после очистки идентификатора совпало со словарём PII;
- иначе среди колонок есть не меньше двух различных зачётных PII-имён.

Если списка колонок нет, решение принимается только по имени таблицы. Каждый INSERT решается независимо: два соседних INSERT с одной PII-колонкой каждый не складываются. Отказ фильтра — тихий пропуск без создания CSV и без строки в логе.

Зачётная колонка:

- совпала со словарём PII;
- не является техническим идентификатором (`id`, `identifier`, `uuid`, `guid`, в том числе с числовым хвостом и формами `user_id` / `userId` / `userid`);
- документный идентификатор (`national_id`, `id_card`, `passport_id`, `ssn_id` и утверждённые аналоги) остаётся зачётным даже с суффиксом id/uuid/guid.

Имена колонок сравниваются без учёта регистра после очистки идентификатора: `email` и `EMAIL` — одна колонка, `email` и `e_mail` — две.

Матчер имени таблицы:

- приводит имя к нижнему регистру Unicode;
- ищет утверждённые термы как подстроку, включая короткие термы (`name`, `pass`, `hash`, `salt`, `tel`, `cp`, `mail`, `state`, `city`, `hp`, `sex`, `dob` и документные термы);
- поддерживает компаунды и разделители: без разделителя, `_`, `-`, `.`, пробел и `__`;
- явно покрывает `user_id`, `userid`, `user-id` и варианты регистра для **имени таблицы**;
- не содержит однобуквенную иглу `u`, голый `id`, IP-адреса и возраст;
- покрывает EN, ES, RU, UK, ID, ZH, PT, FR, DE, IT, малайский, паспортные и национальные идентификаторы.

До положительного совпадения проверяется стоп-список. После приведения к нижнему регистру и удаления `_`, `-`, `.`, пробелов точное компактное имя не должно быть одним из:

`productname`, `filename`, `displayname`, `orderstate`, `filehash`, `settings`.

Исключение `settings` относится только к имени таблицы: `settings(email, phone)` проходит по двум колонкам, `settings(email, status)` не проходит. Полный утверждённый словарь и его конфигурации реализованы и тестируются в `internal/pii`.

Фильтр применяется к SQL (`INSERT` и табличные `.sql`). Excel-листы не проверяются матчером PII.

После отказа PII по INSERT **не разбирать** тело `VALUES` в ячейки: пропустить хвост statement до `;` / следующего statement, учитывая кавычки и комментарии.

### 4.2. Табличные `.sql`

Детектор **по первой непустой строке**, не сканировать весь файл в поисках `INSERT`:

- строка — шапка таблицы, не SQL-выражение (не начинается как `INSERT` / `CREATE` / `UPDATE` / `DELETE` / `WITH` / `BEGIN` / `ALTER` / `DROP` / `REPLACE` / `TRUNCATE` / `SELECT` / `SET` / `CALL` / `GRANT` / `REVOKE` / `LOAD` / `EXEC` / `EXECUTE` / `MERGE` / `USE` / `SHOW` / `EXPLAIN` / `DESCRIBE` / `DESC` / `LOCK` / `UNLOCK` / `DO` / `PRAGMA` / `DECLARE` / `IF` / `COPY` / `PRINT` и не `INSERT` после префиксов; строка-комментарий `--` / `/*` — это SQL, не шапка);
- разделитель — один из: запятая, точка с запятой, таб. Выбрать по первой строке тот, который даёт больше полей (≥ 2 непустых). Пустое поле внутри шапки считается колонкой, но пустой хвост после разделителя не превращает одноколоночную строку в таблицу. Если ни один разделитель не даёт ≥2 полей или строка — SQL, идти в обычный разбор `INSERT`;
- первая логическая запись ограничена 1 MiB. Перевод строки внутри закрытых CSV-кавычек относится к той же записи; незакрытая запись не склеивается сверх лимита.

Имя CSV: `{stem}.sql` → `{stem}.csv` в той же директории после того же санитайза Windows, что у имени таблицы (§5). Пример: `GameSalad.sql` → `GameSalad.csv`. Ключ записи тот же, что у INSERT: `(директория, основа имени)`. Варианты `(n)` не плодить.

PII тот же, что у INSERT: имя таблицы = stem файла без расширения; колонки = шапка. Писать CSV, если stem прошёл `pii.Match` **или** `pii.MatchColumns(шапка)`. Иначе файла CSV нет.

Одна `warn` на такой файл: путь и причина, что это не INSERT, а таблица. Без дампа строк. Warn есть и при отказе PII.

Записывать CSV в формате §6 (кавычки, запятая, LF, без BOM), не копируя исходные байты. Заголовок становится первой строкой CSV, за ним идут строки данных. Первую строку использовать для определения формата, затем читать файл последовательно, не загружая его целиком в память.

После полной обработки табличного `.sql` исходник удалить по §15 (если из него получен CSV). Если PII отказал — исходник **оставить**.

## 5. Соответствие INSERT → CSV

- CSV создаётся **в той же директории**, что и исходный `.sql`.
- Имя файла = имя таблицы **без схемы**, после санитайза Windows (§ ниже).
- Ключ склейки: `(директория .sql, санитайзнутое имя таблицы)`.
- **Все успешные `INSERT` с одним ключом в одном запуске сначала склеиваются в один логический CSV.** Не плодить `{table}(1).csv` на каждый следующий INSERT в ту же таблицу.
- После завершения всех записей в общий CSV файл нарезается по §14, если строк данных больше 4_000_000.
- Заголовок CSV пишется **один раз**: из **самого верхнего успешного** INSERT этого ключа, **если** у него есть список колонок. Если верхний успешный INSERT без списка колонок — шапки нет, ширина файла = первая строка `VALUES`. «Самый верхний» = первый успешный INSERT в порядке обхода: `.sql` по возрастанию пути, внутри файла сверху вниз. Пул воркеров **не** должен подменять этот порядок «кто первый добежал»: разбор VALUES можно параллелить, **Commit в CSV ключа — строго по порядку** `(путь файла, смещение INSERT)`.
- У последующих INSERT того же ключа список колонок в CSV **не пишется**. В файл дописываются только строки данных из `VALUES`. Сопоставление идёт **по порядку значений**, не по именам колонок второго INSERT.
- Та же таблица в **разных** папках → разные CSV (каждый рядом со своим `.sql`).
- Пропущенный INSERT (SELECT / SET / битый / отказ PII / все строки VALUES отброшены из‑за лишней ширины) не становится заголовком и не открывает файл.
- CSV от SQL и CSV от Excel — разные потоки: лист Excel **не** дописывается в `{table}.csv` от INSERT, даже если имена совпали. Имя Excel-CSV задаётся §13.

Имя файла (только при **первом** успешном INSERT ключа в этом запуске):

- недопустимые для Windows символы в имени таблицы (`<>:"/\|?*` и управляющие) заменить на `_`;
- точки и пробелы в конце имени обрезать;
- зарезервированные имена Windows (`CON`, `PRN`, `AUX`, `NUL`, `COM1`…`COM9`, `LPT1`…`LPT9`) префиксить `_`;
- если после чистки имя пустое — использовать `table`;
- основу ограничить 251 кодовой единицей UTF-16, чтобы вместе с `.csv` компонент имени не превышал лимит Windows в 255 единиц; при усечении добавить стабильный hash-суффикс, чтобы разные длинные имена не склеились;
- итог до нарезки: `{table}.csv`;
- если такой файл **уже лежит на диске**, при первом успешном INSERT этого ключа в запуске целевой `{table}.csv` заменить новым содержимым;
- последующие INSERT **этого запуска** с тем же ключом дописывают строки в этот же файл без повторного заголовка;
- варианты `{table}(n).csv` не создаются. Части нарезки — только `{table}_2.csv`, `{table}_3.csv`, … (§14).

Перезапись при создании ключа касается только точного целевого имени. Другие CSV в директории не удаляются, кроме случая, когда они становятся частями нарезки этого же stem по §14.

## 6. Формат CSV

Общий для SQL и Excel. Нарезка §14 **не** меняет формат ячейки.

| Правило | Значение |
|---|---|
| Кодировка | UTF-8 **without signature** (без BOM) |
| Разделитель | `,` (запятая) |
| Перевод строки | `\n` (LF) |
| Каждая ячейка | всегда в двойных кавычках `"..."` |
| Экранирование `"` внутри значения | `""` (стандарт CSV) |
| `NULL` (только SQL) | пустая ячейка `""` |
| Пустая / отсутствующая ячейка | пустая ячейка `""` (кавычки ставятся всегда, вариант `,,` без кавычек не используется) |

Заголовок есть у CSV от Excel и у CSV от SQL **с** списком колонок. CSV от `INSERT INTO t VALUES (...)` (без списка колонок) шапки не имеет.

Заголовок SQL (первый успешный INSERT ключа **со** списком колонок, §5):

- взять список колонок из `INSERT INTO t (col1, col2, ...)`;
- вычистить `INSERT`, `INTO`, имя таблицы, `VALUES` и прочий SQL;
- из имени колонки убрать любое обрамление и служебные символы в любых комбинациях: `` ` ``, `"`, `'`, `[`, `]`, `\`, `/`, а также пробелы по краям;
- в CSV: `"col1","col2","col3"`.

Заголовок Excel (§13): **первая строка листа** — шапка таблицы, пишется первой строкой CSV в том же формате кавычек. INSERT в Excel не ищется и не разбирается: лист — таблица ячеек. Последующие строки листа — строки данных. Ширина заголовка = ширина листа (max колонок среди записанных строк); короткую первую строку дополнить `""`.

Арность строки `VALUES` относительно ширины ключа: число колонок заголовка, а если шапки нет — длина первой строки `VALUES` первого успешного INSERT ключа (у последующих INSERT это ширина первого, не их собственный список):

- значений **меньше**, чем эта ширина → недостающие ячейки дополнить пустыми `""`, строку записать;
- значений **больше**, чем эта ширина → пропустить **только эту строку** `VALUES`; остальные валидные строки того же `INSERT` записать. Если после разбора не осталось ни одной валидной строки — CSV из этого INSERT не создавать (как при пустом `VALUES`).

Техника записи SQL: строки одного INSERT держатся в памяти до 1 MiB, затем запись продолжается через временный файл в целевой директории. INSERT полностью разобран и проверен до публикации в CSV. Если CSV ключа ещё нет — подготовленный результат атомарно заменяет целевой `{table}.csv`; если CSV ключа уже есть в этом запуске — к нему дописываются только строки данных без заголовка. Провал дописывания откатывает CSV к прежнему размеру. Весь набор строк всех INSERT в памяти не копится (§9).

Перед обработкой незавершённой директории удалить только служебные файлы `.2csv-*.tmp`, оставшиеся после аварийного прерывания прошлого запуска. Готовые верхние папки ради такой очистки не обходить.

Данные SQL: каждая строка `VALUES` → одна строка CSV. Значения писать как текст, без вычисления SQL-выражений.

## 7. Списки состояний и `_log.txt`

В выбранном корне программа ведёт четыре независимых списка имён **верхних** папок:

| Файл | Когда папка записывается |
|---|---|
| `_convert_done_.txt` | конвертация `.sql`, `.xlsx` или `.xls` создала хотя бы один CSV |
| `_convert_passed_.txt` | этап конвертации завершился без результата: подходящих файлов нет, всё отсеял PII-фильтр или книги не дали CSV |
| `_splitter_done_.txt` | нарезан хотя бы один созданный или заранее лежавший `.csv` / `.txt` |
| `_splitter_passed_.txt` | этап нарезки завершился без результата: подходящих файлов нет или все они не превышают порог |

- Конвертация и нарезка независимы. Папка из любого `_convert_*` не конвертируется повторно, а папка из любого `_splitter_*` повторно не нарезается. Целиком папка исключается из обхода только после закрытия обоих этапов.
- Ошибка конвертации, нарезки, обхода, публикации результата или записи состояния не закрывает этап. Папка автоматически повторит незавершённый этап при следующем запуске.
- Исходники удаляются после записи состояний. Ошибка удаления оставляет исходник на месте, возвращает код `3`, но не откатывает уже записанное состояние; для повторной обработки оператор удаляет имя папки из списка соответствующего этапа.
- CSV, созданные в текущем запуске, проверяются на нарезку как часть их публикации, даже если этап заранее лежавших файлов уже закрыт.
- Формат списков: одно имя верхней папки на строку, UTF-8 без BOM, LF, накопительная допись. Оборванная последняя строка отбрасывается. На Windows сравнение имён выполняется без учёта регистра.
- Имя папки записывается только после завершения всех её рабочих файлов и успешной фиксации соответствующих этапов. Порядок строк определяется порядком завершения папок и не обязан быть алфавитным.
- Файлы непосредственно в выбранном корне не записываются в списки и обрабатываются при каждом запуске.
- Для повторного запуска этапа оператор удаляет имя папки из соответствующего списка. Флага `--force` нет.
- Старый `converted.txt` не читается и не пишется. Если он существует, он считается обычным `.txt` и может участвовать в нарезке.

`{корень}\_log.txt` накапливает вывод запусков, кроме обновляемой строки прогресса. Каждый запуск начинается с заголовка с датой, временем и путём корня. Ошибка открытия или записи файлового журнала не останавливает обработку, пока доступен stderr.

## 8. Ошибки и логирование

Политика: **не падать на ошибке файла/INSERT/книги Excel/нарезки/удаления исходника**. Пропустить единицу работы, идти дальше.

Единицы пропуска (процесс не останавливают):

- один `.sql`, который нельзя открыть/прочитать;
- один `INSERT`, который нельзя разобрать (битый синтаксис / незакрытый / неожиданный хвост);
- одна строка `VALUES` с числом значений больше ширины ключа (§6) — остальные строки того же INSERT не отбрасываются; в лог один `error` на INSERT с числом таких пропусков, без тел ячеек;
- один `.xlsx`/`.xls`, который нельзя открыть/разобрать, защищён паролем, битый;
- один `.xlsx`/`.xls` с **более чем 5 листами** — книгу целиком не преобразовывать (§13);
- один `.csv`, который нельзя прочитать или нарезать;
- один CSV, который нельзя создать (права, диск, блокировка антивируса);
- один исходник, который нельзя удалить после обработки (§15);
- ошибка чтения списка состояния выводится в stderr, список считается пустым и обход продолжается;
- ошибка дописи списка состояния не закрывает этап и учитывается в коде выхода;
- ошибка открытия или записи `_log.txt` выводится в stderr; отсутствие файлового журнала не отменяет обработку и само по себе не меняет код выхода.

Падать (exit ≠ 0) только если:

- нет выбранного корня (`C:\Source\db` или `C:\Source\combo`);
- корень есть, но это не директория;
- этот корень уже обрабатывается другим экземпляром `2csv`;
- после старта нельзя писать логи в stderr.

Вывод пишется в консоль (stderr) и дублируется в `_log.txt`, кроме обновляемой строки прогресса. В консоль идёт:

- `папка в обработке: <имя> (<N> с)` — висящая строка. `N` — целые секунды с момента, когда папка стала активной. Обновлять **раз в секунду**. Верхних папок может быть **несколько сразу** (§9): в строке перечислить активные имена (стабильный порядок) либо самую давнюю, если все не влезают; путь файла, счётчик файлов, INSERT и ячейки в эту строку не писать;
- итог папки:
  - нет рабочих файлов: `папка <имя>: нет файлов`, этапы получают `*_passed_`;
  - создан хотя бы один CSV или нарезан файл: `папка обработана: <имя>`, соответствующий этап получает `*_done_`;
  - рабочие файлы были, но 0 CSV без технической ошибки: `error: папка <имя>: не создано ни одного CSV: <причина>`, конвертация получает `_convert_passed_`;
  - техническая ошибка: `error: папка <имя>: обработана с ошибками` или `не нарезать`, незавершённые этапы состояния не получают;
- `warn` один раз на табличный `.sql`: путь и что это не INSERT, а таблица;
- ошибка открытия, записи CSV, разбора INSERT, обработки Excel, нарезки или удаления исходника: `error` с путём, таблицей если есть, и причиной. Для строк `VALUES` с лишними значениями записывать одну ошибку на INSERT со счётчиком. Уже записанный CSV не удалять;
- ошибки чтения/дописи списков состояний и сбой воркера.

Если хотя бы один файл завершился с ошибкой до записи состояния, имя папки не добавляется в итоговый список, даже если другие файлы уже создали CSV. Ошибки записываются в журнал, исходники не удаляются, а процесс после завершения обхода возвращает код `3`. Ошибка удаления исходника также даёт код `3`, но возникает уже после записи состояния и не отменяет его. Если CSV не создан и технических ошибок не было, указать реальную причину (нечего конвертировать / всё отсеял фильтр), без тел VALUES и содержимого ячеек.

Не логировать каждый успешный INSERT, каждый PII-пропуск, каждый `SELECT`/`SET`, каждый лист, каждый CSV, каждый успешный split, каждый успешный delete исходника, пропуск книги с >5 листами как отдельную строку файла, прогресс по файлам и итоговую сводку. Не логировать содержимое ячеек и строк данных.

## 9. Производительность и ресурсы

- Потоковый парсер SQL: конечный автомат / сканер по `io.Reader`.
- Не держать в памяти весь SQL и не буферизовать все CSV одного SQL-файла, если можно писать по мере разбора INSERT.
- Excel: не держать в памяти сразу все листы, если библиотека позволяет читать лист за листом / строки потока. Книгу с >5 листами отсекать **до** записи CSV, как только известен счётчик листов.
- Нарезка CSV — потоком по строкам, не `ReadFile` всего файла (§14).
- **Один глобальный пул** воркеров: `N = min(GOMAXPROCS, 16)`, не меньше 1. Каждый свободный воркер берёт следующую задачу из общей очереди и не закрепляется за одной верхней папкой.
- Единица работы SQL: один `INSERT ... VALUES` (после того как сканер нашёл границы statement). Один гигантский INSERT остаётся одним заданием — внутренности одной пачки VALUES этим пулом не режутся.
- Приоритет очереди (выше = раньше):
  1. INSERT / строки текущего уже открытого `.sql`;
  2. другие директории той же верхней папки;
  3. другие верхние папки.
- Разбор VALUES разных INSERT можно выполнять параллельно. **Запись (Commit) в один общий CSV выполняется строго в порядке исходных файлов и расположения INSERT**, а не в порядке завершения воркеров.
- Excel одной директории не начинать, пока все SQL этой директории не закрыты (чтобы лист не вклинился между двумя INSERT одного SQL-ключа). Нарезка ключа — только после закрытия ключа. Удаление исходника — только после закрытия и нарезки CSV, которые этот файл породил (§15).
- Допись списков состояний сериализована и выполняется только после полного завершения конкретной верхней папки (все её директории, конвертация и нарезка).
- Одновременный запуск двух экземпляров для одного корня запрещён межпроцессным lock: второй экземпляр завершается с ошибкой, чтобы не повредить CSV и состояния. После завершения или аварийного закрытия процесса lock освобождается операционной системой.
- Два SQL в одной папке могут писать в CSV одной таблицы. Такая запись выполняется последовательно для каждого общего CSV, а очередь Commit сохраняет порядок исходных файлов. Заголовок берётся по правилу §5.
- Гонки имён CSV: SQL и Excel в одной папке могут претендовать на одно целевое имя — замену `{name}.csv` сериализовать в пределах директории (`Registry` / эквивалент); разные ключи не дописываются друг в друга.
- Ранний PII-reject: после решения «не писать» не парсить ячейки VALUES.

## 10. Интерфейс запуска

Консоль, без GUI.

```text
2csv
```

После запуска (кроме `--help`) программа печатает `combo/db:` и читает одну строку stdin. Допустимы только `combo` и `db` (пробелы по краям отбрасываются, регистр не важен). Иной ответ, пустая строка или EOF — ошибка, exit 2, диск не трогается.

Ожидаемое поведение:

- `db` → корень `C:\Source\db`; `combo` → корень `C:\Source\combo`;
- нет выбранного корня → ошибка, exit 1;
- есть корень → чтение состояний, обход незавершённых этапов, конвертация SQL и Excel, нарезка `.csv` / `.txt` по §14, фиксация состояний и удаление подтверждённых исходников по §15;
- exit 0 означает завершение без ошибок, exit 3 — обход закончен, но один или несколько файлов либо внутренних этапов завершились с ошибкой.

Флаг `--help` допустим и **не** спрашивает `combo/db`. Интерактивный ввод разрешён **только** для выбора `combo`/`db`; CLI-флага пути нет.

## 11. Вне scope

- не **править** содержимое исходных `.sql`, `.xlsx` и `.xls` (не перезаписывать, не обрезать); удаление после обработки — §15, это не «правка»;
- не удалять CSV, которые не являются целевым именем ключа и не являются частями нарезки этого ключа (`{stem}_2.csv`, …);
- не упаковывать CSV в архив;
- не ходить выше выбранного корня (`C:\Source\db` или `C:\Source\combo`);
- не конвертировать `INSERT ... SELECT` и прочий SQL, кроме табличных дампов §4.2;
- не конвертировать `.xlsm` / `.xlsb` / `.ods`;
- не выполнять макросы Excel и не запускать Microsoft Excel;
- не резать один `INSERT ... VALUES` на несколько воркеров внутри одной пачки строк;
- не делать веб-сервер, конфиги, БД, тесты на реальном `C:\Source\db` или `C:\Source\combo` как обязательный шаг разработки (для разработки — фикстуры в репозитории).

## 12. Критерий готовности

Работа считается выполненной, когда:

1. При отсутствии выбранного корня приложение падает с понятной ошибкой.
2. При наличии корня в директории каждого прошедшего PII-фильтр и успешно разобранного `.sql` лежит CSV по правилам §§4, 4.1, 4.2, 5–6 и при необходимости части §14: INSERT одной таблицы в одной папке сначала один логический файл; табличный `.sql` — `{stem}.csv`.
3. При наличии корня у каждого успешно разобранного `.xlsx`/`.xls` (не больше 5 листов) рядом лежат CSV по §13: один лист — один логический CSV; больше 5 листов — ни одного CSV от этой книги.
4. Любой `.csv` или `.txt`, который должен пройти нарезку, разрезан по §14, если в нём больше 4_000_000 строк данных. Правило одинаково для созданных программой и существовавших до запуска файлов.
5. Исходный `.sql` / `.xlsx` / `.xls`, из которого получен хотя бы один CSV и который завершился без ошибок, удалён только после надёжной публикации результата и фиксации состояния (§15). Файл без CSV или с ошибкой не удаляется.
6. Четыре списка §7 независимо фиксируют завершение конвертации и нарезки. Ошибка не закрывает этап; файлы непосредственно в корне не записываются в списки.
7. Ошибки отдельных файлов/INSERT/книг/нарезки/удаления не останавливают обход; в логе — прогресс папки с секундами, итог папки по §8, warn табличного `.sql`, провал единицы с причиной при сохранённом CSV.
8. Глобальный пул воркеров работает по §9: INSERT разных ключей и разные папки могут идти сразу; Commit одного ключа сохраняет порядок «сверху вниз».
9. Приложение запускается из консоли одной командой; корень выбирается ответом `combo` или `db`.

## 13. Excel (`.xlsx` / `.xls`) → CSV

- CSV создаётся **в той же директории**, что и исходный `.xlsx` или `.xls`.
- Исходный Excel **не править**. После полной обработки книги, если из неё получен хотя бы один CSV, исходник **удалить** (§15). Книгу с >5 листами, пустую, битую или без CSV — не удалять.
- Считать **все** листы книги, включая скрытые и очень скрытые.
- Chart/dialog sheets также входят в лимит пяти; как нетабличные листы они не создают CSV.
- Если листов **больше 5** (`count > 5`) — **всю книгу не преобразовывать**: ни одного CSV от этого файла. 5 листов — ещё в scope.
- Если листов 1…5 — **каждый лист → отдельный логический CSV** (в том числе скрытый). Не склеивать листы в один файл.
- Пустой лист (нет ни одной ячейки с непустым текстом после нормализации) — CSV **не** создавать. Остальные листы той же книги (если они не пустые) всё равно писать.
- Если после отсечения пустых листов не создано ни одного CSV, сама книга не даёт CSV. Итоговое состояние верхней папки определяется по §7.
- Имя файла: `{книга}_{лист}.csv`, где `книга` — имя файла без расширения (и для `.xlsx`, и для `.xls`), `лист` — имя листа; обе части прогнать через тот же санитайз Windows, что и имя таблицы (§5). Пустая часть после чистки: для книги — `book`, для листа — `sheet`.
- После объединения основы `{книга}_{лист}` применить общий лимит 251 кодовой единицы UTF-16 перед добавлением `.csv`; при усечении сохранить стабильный hash-суффикс.
- Если `{книга}_{лист}.csv` лежал на диске до запуска, при первом создании этого ключа файл заменить. Если это имя уже занято результатом другого источника текущего запуска, второй результат отклоняется, а его исходник сохраняется. Варианты `(n)` не создавать.
- Два разных Excel-файла в одной папке с одинаковым именем листа дают разные префиксы книги (`a_Sheet1.csv` и `b_Sheet1.csv`).
- Склейки листов между книгами и с SQL-INSERT **нет**: каждый успешный лист — отдельная запись на этот запуск. Excel не разбирается как SQL: в книге нет INSERT, конвертируется таблица листа.
- Строки: первая непустого листа — **заголовок CSV** (шапка таблицы); дальше сверху вниз строки данных. Не писать хвостовые полностью пустые строки. Ширина листа = максимум колонок среди записанных строк (включая шапку); более короткую строку дополнить `""`.
- Объединённые ячейки: значение в верхней левой клетке объединения, остальные клетки объединения — пустые `""` (как обычно отдаёт библиотека).
- Формулы: в CSV писать **кэшированное/отображаемое значение как текст**, не текст формулы (`=A1+1`). Нет кэша — пустая ячейка `""`.
- Числа, даты, булевы: как текст, который даёт библиотека (без своего пересчёта часовых поясов и без локали машины как отдельной политики).
- Техника записи: лист сначала во временный файл в целевой директории, в итоговый CSV — только после успеха этого листа. Провал второго листа не удаляет CSV первого листа той же книги.
- После завершения записи CSV листа — нарезка по §14, если строк данных больше 4_000_000.
- `.xls` больше 256 MiB отклоняется до загрузки в память. Обработка `.xls` сериализована, потому что библиотека читает книгу целиком.
- Для `.xlsx` ограничен распакованный объём книги 4 GiB; XML листа больше 16 MiB переносится во временный файл вместо удержания целиком в памяти.
- Пароль / битый файл / не Excel по содержимому: пропустить файл, ошибка в лог, CSV не создавать.

## 14. Нарезка CSV и TXT

Применяется к **любому** `.csv` или `.txt` в открытом для нарезки этапе верхней папки и в корне: и к файлу, который только что склеили из INSERT/листа, и к файлу, который лежал заранее.

Порог и размер куска:

- если строк **данных** ≤ 4_000_000 — файл не трогать;
- если строк данных > 4_000_000 — разрезать так, чтобы каждая часть содержала **не больше 2_000_000** строк данных; последняя часть может быть короче;
- пример: 4_200_001 строка данных → 2_000_000 + 2_000_000 + 200_001.

Что считать строкой данных:

- заголовок (если он есть) в порог **не** входит и **копируется в каждый кусок**;
- CSV, созданный программой без заголовка (`INSERT` без списка колонок): все строки файла считаются данными;
- чужой / заранее лежавший `.csv`: первая непустая строка считается заголовком и копируется в каждый кусок; остальные строки — данные. Пустые хвостовые строки не писать в куски.
- `.txt`: каждая физическая строка до `\n` считается записью, заголовка нет, CSV-кавычки не интерпретируются; исходные байты и CRLF сохраняются. Пустые строки между данными считаются строками, хвостовые пустые строки отбрасываются.

Имена:

- первый кусок сохраняет исходное имя и расширение;
- дальше только суффикс `_2`, `_3`, `_4`, … — `{stem}_2.csv`, `{stem}_3.csv` либо `{stem}_2.txt`, `{stem}_3.txt`;
- не использовать `{stem}(n).csv` и не использовать `_part`.
- `{stem}` — имя файла без расширения. Если имя сформировано программой, оно уже приведено к допустимому для Windows виду. Ограничение 251 кодовой единицы UTF-16 применяется к полной основе с суффиксом `_N` так же, как к обычному имени: при усечении добавляется стабильный hash, а суффикс `_N` сохраняется.

Столкновения:

- Если `{stem}_2.csv` уже лежит на диске, при новой нарезке `{stem}.csv` он **заменяется** второй частью нового набора. Варианты `(n)` не создавать.
- `readme.txt`, `_log.txt`, четыре списка §7 и `.2csv-*.tmp` не нарезать.
- Уже короткие части (`≤ 2_000_000` строк данных) повторно не резать. Файл вида `{stem}_2.csv` с более чем 4_000_000 строк данных режется от **своего** имени: `{stem}_2.csv` + `{stem}_2_2.csv` + …

Техника:

- поток по строкам, не грузить весь CSV в память;
- писать куски во временные `.2csv-*.tmp`, затем атомарно заменить цели: сначала части `_2`…`_N`, затем усечь/заменить первый `{stem}.csv`;
- исходный файл не заменять, пока все части не будут успешно подготовлены;
- провал нарезки: исходный `{stem}.csv` оставить как был (до нарезки); частично созданные новые части этого прогона убрать, если можно; уже существующие до прогона `{stem}_2.csv` не уничтожать «на всякий случай», если замена не завершилась;
- CSV, создаваемый программой в текущем запуске, нарезать только после завершения всех записей в этот файл.

Нарезка сама по себе даёт `_splitter_done_` по §7, если появилась хотя бы одна новая часть или успешно переписан разрезанный файл.

## 15. Удаление исходников после обработки

Заказчик разрешил удалять исходники. Это не отменяет потоковую конвертацию и не разрешает править файл «на месте».

Удалять **только**:

- `.sql`, из которого в этом запуске получен хотя бы один CSV (INSERT или табличный дамп);
- `.xlsx` / `.xls`, из которого в этом запуске получен хотя бы один CSV.

Не удалять:

- файл, который не открылся, битый, с паролем;
- `.sql`, который целиком отсеял PII или не дал ни одного CSV;
- книгу с >5 листами или без непустых листов;
- `.csv` / `.txt` как исходники конвертации: при нарезке исходный файл безопасно заменяется готовыми частями по §14;
- `_log.txt` и списки состояний §7.

Когда:

- **после** полной обработки этого файла (все INSERT/листы дочитаны);
- **после** Commit CSV, которые этот файл породил;
- **после** нарезки этих ключей, если она нужна;
- **после** успешной записи требуемых списков состояния верхней папки; для файлов непосредственно в корне этот шаг отсутствует;
- **никогда до** подтверждения результата: сначала результат и состояние на диске, потом `os.Remove` исходника.

Ошибка удаления считается ошибкой обработки: записать `error` с путём и причиной, не удалять готовый CSV и не отменять уже записанное состояние, продолжить обход и завершить процесс с кодом `3`. Исходник остаётся на диске. Для автоматической повторной обработки оператор удаляет имя папки из списка соответствующего этапа.

Повторный запуск: этап, уже записанный в список состояния, не выполняется повторно. Если результат этапа не был записан, оставшиеся `.sql`/Excel/CSV/TXT обрабатываются заново; целевые CSV создаются по §§5 и 13.
