# Constraints and Policy

Документ задаёт обязательные правила для реализации консольного конвертера SQL/Excel → CSV. Любое отклонение от этого документа требует явного согласования с заказчиком.

## 1. Цель

После запуска спросить `combo` или `db` и рекурсивно пройти выбранный корень (`C:\Source\combo` или `C:\Source\db`), на любой глубине найти:

- файлы `.sql` — извлечь только операторы `INSERT` с данными и сохранить CSV **рядом с исходным SQL**;
- файлы `.xlsx` и `.xls` — сохранить CSV **рядом с исходным Excel** по правилам §13.

После обработки записать `converted.txt` в выбранный корень.

Конвертер — консольное приложение. Исходной папки на момент разработки может не быть: это нормально. Если при запуске выбранный корень отсутствует — приложение **завершается с ошибкой** (ненулевой код выхода), ничего не создаёт.

## 2. Язык и стек

**Язык: Go.**

Почему не Python:

- файлов много, отдельные файлы могут быть большими;
- нужен потоковый разбор SQL (не `ReadFile` / не загрузка всего SQL в память);
- независимые файлы можно обрабатывать конкурентно с контролируемым пулом воркеров;
- результат — один бинарник без интерпретатора и venv.

Запрещено:

- подключать полный SQL-движок или ORM;
- тащить тяжёлые парсеры «всего SQL»;
- читать весь `.sql` в `[]byte` / `string`, если размер может быть большим;
- писать свой разбор ZIP/XML Excel или BIFF/OLE `.xls` с нуля.

Разрешено: стандартная библиотека Go + минимальные зависимости только если без них нельзя закрыть требование. Для `.xlsx` и `.xls` допустимы библиотеки чтения Excel (например `excelize` для `.xlsx`), без Excel COM и без запуска Excel.

## 3. Вход

| Правило | Значение |
|---|---|
| Корень | один из двух жёстких путей: `C:\Source\db` (ответ `db`) или `C:\Source\combo` (ответ `combo`); CLI-флага пути нет |
| Выбор корня | после запуска (кроме `--help`) приглашение `combo/db:`; регистр не важен; пустой / неизвестный / EOF — ошибка, exit 2 |
| Нет корня | `fatal`: сообщение в stderr, exit ≠ 0 |
| SQL | `.sql`, без учёта регистра (`.SQL`, `.Sql`) |
| Excel | `.xlsx` и `.xls`, без учёта регистра (`.XLSX`, `.Xlsx`, `.XLS`, `.Xls`) |
| Не в scope | `.xlsm`, `.xlsb`, `.ods` и прочие таблицы — игнорировать как обычные не-SQL/не-Excel файлы |
| Кодировка SQL | вход считается UTF-8; BOM в начале файла отбрасывается; байты значений переносятся в CSV без перекодировки и без автодетекта cp1251/UTF-16 |
| Обход | рекурсивный, все уровни вложенности |
| Симлинки | не следовать (защита от циклов) |
| Прочие файлы | игнорировать |
| Файл в выбранном корне (не в подпапке) | CSV рядом создавать; в `converted.txt` эту ситуацию не отражать |

## 4. Что извлекать из SQL

Извлекать **только** `INSERT` с данными в форме `VALUES`.

В scope:

- `INSERT INTO table (...) VALUES (...);`
- `INSERT INTO table (...) VALUES (...), (...), (...);` — один INSERT даёт несколько строк данных в CSV этой таблицы (не отдельный файл на каждую строку `VALUES`)
- опциональные префиксы вроде `INSERT IGNORE`, `INSERT OR REPLACE`, `LOW_PRIORITY`, `DELAYED` — таблица и колонки всё равно извлекаются
- идентификаторы: `` `table` ``, `"table"`, `[table]`, `schema.table` (имя файла = имя таблицы **без** схемы)
- строковые литералы `'...'`, `"..."`; экранирование `''` внутри одинарных кавычек
- внутри `'...'` символ `\` экранирует следующий символ: `\'` не закрывает литерал, `\\` — один обратный слэш. Escape-последовательности не разворачиваются: `\n` остаётся двумя символами текста
- двойные кавычки трактуются по позиции: в позиции имени таблицы или колонки — идентификатор, в позиции значения внутри `VALUES` — строковый литерал
- значения в скобках: числа, `NULL`, строки, hex-литералы как текст ячейки

Вне scope (пропустить INSERT, в консоль не писать — см. §8):

- `INSERT ... SELECT ...`
- `INSERT ... SET col=val` (нет `VALUES`)
- `INSERT` без списка колонок: `INSERT INTO t VALUES (...)`
- DDL, `UPDATE`, `DELETE`, хранимые процедуры, комментарии сами по себе
- битый / незакрытый `INSERT`
- `INSERT` с пустым набором строк данных (после `VALUES` нет ни одной группы значений): CSV из одного заголовка не создаётся

Комментарии `-- ...` и `/* ... */` не должны ломать поиск `INSERT`. MySQL-хинты вида `/*!40101 ... */` трактуются как обычный блочный комментарий, их содержимое игнорируется целиком. Строки внутри кавычек, похожие на SQL, не считаются синтаксисом.

## 5. Соответствие INSERT → CSV

- CSV создаётся **в той же директории**, что и исходный `.sql`.
- Имя файла = имя таблицы **без схемы**, после санитайза Windows (§ ниже).
- Ключ склейки: `(директория .sql, санитайзнутое имя таблицы)`.
- **Все успешные `INSERT` с одним ключом в одном запуске → один CSV-файл.** Не плодить `{table}(1).csv` на каждый следующий INSERT в ту же таблицу.
- Заголовок CSV пишется **один раз**: из **самого верхнего успешного** INSERT этого ключа. «Самый верхний» = первый успешный INSERT в порядке обхода: `.sql` по возрастанию пути, внутри файла сверху вниз. Пул воркеров не должен подменять этот порядок «кто первый добежал».
- У последующих INSERT того же ключа список колонок в CSV **не пишется**. В файл дописываются только строки данных из `VALUES`. Сопоставление идёт **по порядку значений**, не по именам колонок второго INSERT.
- Та же таблица в **разных** папках → разные CSV (каждый рядом со своим `.sql`).
- Пропущенный INSERT (SELECT / SET / битый / лишние значения) не становится заголовком и не открывает файл.
- CSV от SQL и CSV от Excel — разные потоки: лист Excel **не** дописывается в `{table}.csv` от INSERT, даже если имена совпали. Имя Excel-CSV задаётся §13.

Имя файла (только при **первом** успешном INSERT ключа в этом запуске):

- недопустимые для Windows символы в имени таблицы (`<>:"/\|?*` и управляющие) заменить на `_`;
- точки и пробелы в конце имени обрезать;
- зарезервированные имена Windows (`CON`, `PRN`, `AUX`, `NUL`, `COM1`…`COM9`, `LPT1`…`LPT9`) префиксить `_`;
- если после чистки имя пустое — использовать `table`;
- итог: `{table}.csv`;
- если такой файл **уже лежит на диске** (чужой / прошлый запуск / CSV от Excel) — `{table}(1).csv`, `(2)`, … первое свободное `n`. Последующие INSERT **этого запуска** с тем же ключом дописывают в **этот** выбранный файл, а не берут следующее `(n)`;
- индекс проверять **в момент первого создания** ключа в запуске, не заранее по кэшу с прошлого прогона.

Нельзя перезаписывать существующие CSV, которые не были созданы этим запуском для данного ключа.

## 6. Формат CSV

Общий для SQL и Excel.

| Правило | Значение |
|---|---|
| Кодировка | UTF-8 **without signature** (без BOM) |
| Разделитель | `,` (запятая) |
| Перевод строки | `\n` (LF) |
| Каждая ячейка | всегда в двойных кавычках `"..."` |
| Экранирование `"` внутри значения | `""` (стандарт CSV) |
| `NULL` (только SQL) | пустая ячейка `""` |
| Пустая / отсутствующая ячейка | пустая ячейка `""` (кавычки ставятся всегда, вариант `,,` без кавычек не используется) |

Заголовок есть и у CSV от SQL, и у CSV от Excel.

Заголовок SQL (первый успешный INSERT ключа, §5):

- взять список колонок из `INSERT INTO t (col1, col2, ...)`;
- вычистить `INSERT`, `INTO`, имя таблицы, `VALUES` и прочий SQL;
- из имени колонки убрать любое обрамление и служебные символы в любых комбинациях: `` ` ``, `"`, `'`, `[`, `]`, `\`, `/`, а также пробелы по краям;
- в CSV: `"col1","col2","col3"`.

Заголовок Excel (§13): **первая строка листа** — шапка таблицы, пишется первой строкой CSV в том же формате кавычек. INSERT в Excel не ищется и не разбирается: лист — таблица ячеек. Последующие строки листа — строки данных. Ширина заголовка = ширина листа (max колонок среди записанных строк); короткую первую строку дополнить `""`.

Арность строки `VALUES` относительно числа колонок **заголовка** (у последующих INSERT ключа это колонки первого успешного INSERT, не их собственный список):

- значений **меньше**, чем колонок заголовка → недостающие ячейки дополнить пустыми `""`, строку записать;
- значений **больше**, чем колонок заголовка → пропустить **весь** этот `INSERT` целиком.

Техника записи SQL: каждый отдельный INSERT сначала пишется во временный файл в целевой директории. После успеха этого INSERT: если CSV ключа ещё нет — переименовать временный файл в `{table}.csv` (или `{table}(n).csv`); если CSV ключа уже есть в этом запуске — дописать к нему только строки данных (без заголовка) и удалить временный. Провал второго INSERT не удаляет и не откатывает CSV, уже полученный от первого. Весь набор строк всех INSERT в памяти не копится (§9).

Данные SQL: каждая строка `VALUES` → одна строка CSV. Значения писать как текст, без вычисления SQL-выражений.

## 7. `converted.txt`

- Путь: `{выбранный корень}\converted.txt` (`C:\Source\db\converted.txt` или `C:\Source\combo\converted.txt`).
- Содержимое: имена **только верхних** папок внутри выбранного корня (прямой ребёнок корня), в которых **был хотя бы один успешно созданный CSV** — от INSERT и/или от Excel-листа.
- Не включать папки без успешной конвертации (в том числе папки, где Excel пропущен из‑за >5 листов и SQL не дал CSV).
- Не включать вложенные пути — только имя верхнего уровня (`Foo`, не `Foo\Bar`).
- Порядок: лексикографический, одно имя на строку, UTF-8 без BOM, LF.
- Если файл уже есть — перезаписать по итогам текущего запуска.
- Если успешных конвертаций не было, но корень существовал — **создать пустой** `converted.txt`.

## 8. Ошибки и логирование

Политика: **не падать на ошибке файла/INSERT/книги Excel**. Пропустить единицу работы, идти дальше.

Единицы пропуска (процесс не останавливают):

- один `.sql`, который нельзя открыть/прочитать;
- один `INSERT`, который нельзя разобрать, у которого нет списка колонок или в котором значений больше, чем колонок (§6);
- один `.xlsx`/`.xls`, который нельзя открыть/разобрать, защищён паролем, битый;
- один `.xlsx`/`.xls` с **более чем 5 листами** — книгу целиком не преобразовывать (§13);
- один CSV, который нельзя создать (права, диск, блокировка антивируса).

Падать (exit ≠ 0) только если:

- нет выбранного корня (`C:\Source\db` или `C:\Source\combo`);
- корень есть, но это не директория;
- после старта нельзя писать логи в stderr.

Лог пишется **только в консоль (stderr)**, файл лога не создаётся. В консоль идёт только:

- `папка в обработке: <имя>` — один раз на верхнюю папку, строка висит до конца этой папки и не повторяется;
- `папка полностью завершена: <имя>` — когда обработаны **все** рабочие файлы этой верхней папки (`.sql`, `.xlsx` и `.xls`);
- критические ошибки (не открыть `.sql`/`.xlsx`/`.xls`, не создать/записать CSV, не записать `converted.txt`, сбой воркера).

Не логировать каждый INSERT, каждый лист, каждый CSV, пропуски SELECT/SET, пропуск книги с >5 листами, прогресс по файлам и итоговую сводку. Не логировать содержимое ячеек и строк данных.

## 9. Производительность и ресурсы

- Потоковый парсер SQL: конечный автомат / сканер по `io.Reader`.
- Не держать в памяти весь SQL и не буферизовать все CSV одного SQL-файла, если можно писать по мере разбора INSERT.
- Excel: не держать в памяти сразу все листы, если библиотека позволяет читать лист за листом / строки потока. Книгу с >5 листами отсекать **до** записи CSV, как только известен счётчик листов.
- Пул воркеров по файлам (например N = `GOMAXPROCS`), запись `converted.txt` — после завершения всех воркеров.
- Гонки SQL: два SQL в одной папке могут писать в одну таблицу — сериализация **по ключу склейки** (директория + имя таблицы). Заголовок должен соответствовать порядку «самый верхний INSERT» (§5), а не порядку завершения воркеров.
- Гонки имён CSV: SQL и Excel в одной папке могут претендовать на пересекающиеся имена — выбор свободного `{name}(n).csv` сериализовать в пределах директории (уже существующий `Registry` / эквивалент).

## 10. Интерфейс запуска

Консоль, без GUI.

```text
2csv
```

После запуска (кроме `--help`) программа печатает `combo/db:` и читает одну строку stdin. Допустимы только `combo` и `db` (пробелы по краям отбрасываются, регистр не важен). Иной ответ, пустая строка или EOF — ошибка, exit 2, диск не трогается.

Ожидаемое поведение:

- `db` → корень `C:\Source\db`; `combo` → корень `C:\Source\combo`;
- нет выбранного корня → ошибка, exit 1;
- есть корень → обход, конвертация SQL и Excel, `converted.txt` в этом корне, exit 0 если корень обработан (даже если часть файлов/INSERT/книг пропущена).

Флаг `--help` допустим и **не** спрашивает `combo/db`. Интерактивный ввод разрешён **только** для выбора `combo`/`db`; CLI-флага пути нет.

## 11. Вне scope

- не менять исходные `.sql`, `.xlsx` и `.xls`;
- не удалять старые CSV;
- не упаковывать CSV в архив;
- не ходить выше выбранного корня (`C:\Source\db` или `C:\Source\combo`);
- не конвертировать `INSERT ... SELECT` и прочий SQL;
- не конвертировать `.xlsm` / `.xlsb` / `.ods`;
- не выполнять макросы Excel и не запускать Microsoft Excel;
- не делать веб-сервер, конфиги, БД, тесты на реальном `C:\Source\db` или `C:\Source\combo` как обязательный шаг разработки (для разработки — фикстуры в репозитории).

## 12. Критерий готовности

Работа считается выполненной, когда:

1. При отсутствии выбранного корня приложение падает с понятной ошибкой.
2. При наличии корня в директории каждого успешно разобранного `.sql` лежит CSV по правилам §§5–6: одна таблица в одной папке — один файл за запуск, заголовок только от верхнего успешного INSERT.
3. При наличии корня у каждого успешно разобранного `.xlsx`/`.xls` (не больше 5 листов) рядом лежат CSV по §13: один лист — один CSV; больше 5 листов — ни одного CSV от этой книги.
4. В `{выбранный корень}\converted.txt` перечислены только верхние папки с хотя бы одной успешной конвертацией (SQL и/или Excel).
5. Ошибки отдельных файлов/INSERT/книг не останавливают обход; в логе только статус папки и критические ошибки.
6. Приложение запускается из консоли одной командой; корень выбирается ответом `combo` или `db`.

## 13. Excel (`.xlsx` / `.xls`) → CSV

- CSV создаётся **в той же директории**, что и исходный `.xlsx` или `.xls`.
- Исходный Excel-файл не менять.
- Считать **все** листы книги, включая скрытые и очень скрытые.
- Если листов **больше 5** (`count > 5`) — **всю книгу не преобразовывать**: ни одного CSV от этого файла. 5 листов — ещё в scope.
- Если листов 1…5 — **каждый лист → отдельный CSV** (в том числе скрытый). Не склеивать листы в один файл.
- Пустой лист (нет ни одной ячейки с непустым текстом после нормализации) — CSV **не** создавать. Остальные листы той же книги (если они не пустые) всё равно писать.
- Если после отсечения пустых листов не создано ни одного CSV — книга не считается успехом для `converted.txt`.
- Имя файла: `{книга}_{лист}.csv`, где `книга` — имя файла без расширения (и для `.xlsx`, и для `.xls`), `лист` — имя листа; обе части прогнать через тот же санитайз Windows, что и имя таблицы (§5). Пустая часть после чистки: для книги — `book`, для листа — `sheet`.
- Если `{книга}_{лист}.csv` уже лежит на диске — `{книга}_{лист}(1).csv`, `(2)`, … первое свободное имя. Не перезаписывать чужие CSV.
- Два разных Excel-файла в одной папке с одинаковым именем листа дают разные префиксы книги (`a_Sheet1.csv` и `b_Sheet1.csv`).
- Склейки листов между книгами и с SQL-INSERT **нет**: каждый успешный лист — свой файл на этот запуск. Excel не разбирается как SQL: в книге нет INSERT, конвертируется таблица листа.
- Строки: первая непустого листа — **заголовок CSV** (шапка таблицы); дальше сверху вниз строки данных. Не писать хвостовые полностью пустые строки. Ширина листа = максимум колонок среди записанных строк (включая шапку); более короткую строку дополнить `""`.
- Объединённые ячейки: значение в верхней левой клетке объединения, остальные клетки объединения — пустые `""` (как обычно отдаёт библиотека).
- Формулы: в CSV писать **кэшированное/отображаемое значение как текст**, не текст формулы (`=A1+1`). Нет кэша — пустая ячейка `""`.
- Числа, даты, булевы: как текст, который даёт библиотека (без своего пересчёта часовых поясов и без локали машины как отдельной политики).
- Техника записи: лист сначала во временный файл в целевой директории, в итоговый CSV — только после успеха этого листа. Провал второго листа не удаляет CSV первого листа той же книги.
- Пароль / битый файл / не Excel по содержимому: пропустить файл, критическая ошибка в лог, CSV не создавать.
